- Nothing changes for an app that only bumps its pin: the new commands below do nothing until you call them. Adopt them one at a time; the README has a section for each.
- **`devkit-test`** finds and runs every `node --test` file in the app (`*.test.ts`, `*.test.tsx`, `*.test.mjs`), skipping dependencies, build output, `external/` and dot-folders such as `.worktrees/`. Set `"test": "devkit-test"` and delete `scripts/dev/run-tests.mjs`. It fails when it finds no tests, and needs `tsx` in the app for TypeScript tests. See "Running tests".
- **Database tests** are named `*.integration.test.ts` (or `.tsx`, `.mjs`). The default run leaves them out; set `"test:integration": "devkit-test --integration"`, which runs only those files, one at a time. Apps that split database tests by folder (for example `apps/api/test/`) rename those files to the suffix.
- **`devkit-wait-for-db`** replaces `scripts/dev/wait-for-db.mjs`: set `"db:wait": "devkit-wait-for-db"` and delete the script. It reads `DATABASE_URL`, needs no app-specific default, and keeps the `DB_WAIT_TIMEOUT_MS` and `DB_WAIT_RETRY_MS` settings.
- **`devkitViteServer(env)`** from `@dynamic-solutions-canada/devkit/vite` replaces the `port`, `host` and `allowedHosts` lines in your Vite `server` block: spread it and keep your own proxy. It also stops the primary checkout's Vite from watching `.worktrees/`. See "Waiting for the database and the Vite server block".
- **`devkit-init`** writes the files every app used to copy by hand, and `devkit-init --check` fails when one is out of date or was edited. Run `npm exec devkit-init` after this bump and after every later one, review and commit the result, and add `"check:devkit": "devkit-init --check"` to `validate`. Keys you added to `package.json`, `paseo.json` and `.claude/settings.json` are kept, and an existing `compose.dev.yml` is left alone. It writes:
  1. `scripts/dev/run-dev.mjs` and the `dev` and lifecycle npm scripts. Move your runner's container-side steps (waiting for the database, migrations or a fresh seed, starting the dev servers) into a `dev:container` npm script first; it sees `DEVKIT_FRESH=1` for `--fresh`. Extra worktree setup steps move from `dev:prepare-worktree` into a `dev:postprepare` script, which the generated one runs after `devkit prepare`.
  2. `paseo.json`, now with a `test` entry.
  3. `scripts/deploy/deploy-over-ssh.mjs` and `deploy:prod`: a verified database dump before every deploy, a health wait that stops with the logs, and the nginx site file installed with `nginx -t` and rollback. Before your next deploy, rename the production compose file to `compose.server.yml`, track `nginx.server.conf` with your real host names, and set any differences (database service, kept dumps, site name) in the new `deploy` block of `devkit.config.mjs`. `DEPLOY_SSH_HOST` and `DEPLOY_REPO_PATH` stay in `.env`. See "Deploying".
  4. `scripts/hooks/generated-file-guard.mjs` and its registration in `.claude/settings.json`: persistent's guard that stops an agent hand-editing a generated file. List generated folders in `scripts/hooks/generated-file-guard.json`; files whose header says they are generated, including everything `devkit-init` writes, are covered without it. persistent deletes its own copy and keeps its JSON file and its test of it.

  To keep your own version of any of these, set `generated: { runner: false }` (or `paseo`, `scripts`, `deploy`, `guard`) in `devkit.config.mjs`.
