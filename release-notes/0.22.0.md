- Nothing changes for an app that only bumps its pin: `devkit-notices` does nothing until you configure it.
- **`devkit-notices`** replaces each app's own `scripts/dev/generate-third-party-notices.mjs`. List your deliverables in a `notices` block in `devkit.config.mjs` (a `title`, the `packages` folders it ships, and its `output` file), set `notices` to `devkit-notices`, and either add `devkit-notices --check` to `validate` (committed files) or run `devkit-notices` in the build (git-ignored files). Then delete your script. See "Third-party notices" in the README.
- The first run changes each notices file once. The "generated by" line now names `devkit-notices`, and entries are sorted by code point, so the order is the same on every machine. Licence text that shipped with Windows line endings is stored with LF.
- Your own packages are left out automatically (the root, workspaces and `file:` links), so the scope-prefix rule in your script goes away.
- It fails on a package with no declared licence and no licence file, and on one declared `UNLICENSED`. Add a private package you may ship to that deliverable's `allow` list; an `allow` entry that is no longer a dependency fails too.
- Run `--check` on Linux x64, where WSL, CI and the images run. Native packages for one platform only are listed as installed there. An arm64 build takes its notices from the x64 list, and differs only in those native packages.
- A Docker build that runs `devkit-notices` copies `devkit.config.mjs` instead of the old script.
